# Aureus Public Naming System

This is the canonical public naming hierarchy for Aureus Automation Lab. It keeps one company identity, one operating system, a small set of Aureus product/proof lines, and clearly subordinate offers and scenarios.

## Canonical Hierarchy

| Level | Canonical public name | Role |
| --- | --- | --- |
| Company | **Aureus Automation Lab** | The public identity and accountable builder |
| Operating layer | **Aureus OS** | The single operating system for planning, execution, validation, evidence, and approval boundaries |
| Product proof | **Aureus CRM Operations** | Full-stack synthetic business-operations product proof |
| Product direction | **Aureus FinEcon** | Reviewed finance and document workflow direction |
| Infrastructure proof | **Aureus Trading Infrastructure** | Private paper-run, risk-first engineering proof |
| Demonstration scenario | **Aureus Sales Workflow** | Approval-gated lead and follow-up workflow example |

Service offers such as **Automation Audit**, **n8n Workflow Review / Build**, **AI Operations System**, and **Product or Internal Tool Build** are ways to engage Aureus Automation Lab. They are not separate brands or operating systems.

## Public Naming Rules

1. **Only Aureus OS is an operating system.** Versions, protocols, supervisors, agents, skills, validators, and internal runtimes are parts of Aureus OS, not public sibling brands.
2. **Public product and proof lines use an Aureus-first name.** A descriptive subtitle may explain the domain, maturity, and evidence boundary.
3. **Repository and implementation names do not define the brand.** Internal Git repository names, branches, workflow numbers, and historical program names remain source aliases only.
4. **Every public proof line carries a maturity label.** Use terms such as `source-backed synthetic proof`, `pilot direction`, or `paper-run architecture`; never let the name imply a stronger outcome.
5. **Legacy wording is allowed only for traceability.** When a historical label must appear, identify it as a legacy alias or module name and point back to the canonical public name.
6. **A new top-level public name requires evidence and governance review.** It must have a distinct buyer problem, owner, source boundary, validation path, maturity status, and no overlap with an existing Aureus line.

## Change Control

Canonical names are enforced on the public front door, project map, proof showroom, capability summary, case-study index, profile settings packet, pin strategy, and current file paths. Public proof directories use the canonical slugs `aureus-os`, `aureus-crm-operations`, `aureus-finecon`, `aureus-trading-infrastructure`, and `aureus-sales-workflow`. An older slug may survive only as a minimal redirect or stub when verified inbound-link evidence makes removal harmful; it must never remain the discoverable home of the current artifact.

Any future rename should update this register first, then the primary public surfaces and validator in the same pull request.
