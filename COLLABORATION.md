# Collaboration

## How Collaboration Starts

A good collaboration starts with the process, not the tool. Useful starting inputs are:

- process: what currently happens from start to finish,
- tools: inboxes, drives, sheets, workflow tools, APIs, chat, or internal systems involved,
- owner: who is responsible for the result and final decision,
- pain points: what breaks, gets delayed, becomes repetitive, or depends on memory,
- success criteria: what the first useful version should prove,
- sensitive data boundary: what must not be exposed, logged, copied, or automated without review.

## First-Slice Approach

The first useful version matters because it creates evidence quickly. Instead of trying to automate everything at once, the first slice should prove one valuable workflow path, make ownership clearer, show where AI helps safely, and reveal the next practical improvement.

Good first slices often look like a structured intake flow, review queue, dashboard slice, document validation path, approval workflow, or AI-assisted draft process with owner review.

## Collaboration Phases

| Phase | Goal | Output | Quality check |
| --- | --- | --- | --- |
| Discovery | Understand the current process, owners, tools, risks, and success criteria | Process map, assumptions, first-slice options | Is the real business problem clear? |
| Architecture | Define data boundaries, tool boundaries, AI role, review states, and validation path | Solution architecture, workflow shape, acceptance criteria | Is the system understandable before it is built? |
| Build | Create the smallest useful workflow, tool, or prototype slice | Working slice, documentation notes, test examples | Does it solve the agreed first problem? |
| Review | Check output quality, edge cases, privacy boundaries, and owner approval flow | QA notes, proof pack, risk notes, improvement list | Can the owner trust what happened and see what needs review? |
| Handoff | Make the system operable without hidden context | Operating notes, runbook, known limits, next-step roadmap | Could another person run or review it later? |
| Next iteration | Decide what to improve after evidence exists | Prioritized backlog, scope recommendation, optional next slice | Is the next step based on proof instead of guesswork? |

## What Good Collaboration Prevents

- building before the problem is understood,
- automating decisions that need review,
- hiding fragile logic in black boxes,
- creating systems nobody can operate later,
- treating AI output as correct without evidence.

## Communication Style

I aim for communication that is:

- concise,
- evidence-based,
- owner-friendly,
- technical when needed,
- honest about uncertainty,
- explicit about blockers and approval needs.

## Boundaries

Strong automation does not remove ownership. It should make ownership clearer.

For each serious workflow, I want these boundaries explicit:

- what is automated,
- what remains human-reviewed,
- what data is sensitive,
- what can fail,
- who approves important actions,
- how the work is validated.
